# WPF → WinUI Workspace and Queue audit

Source snapshot: [467c0754ffc0](https://github.com/hyn1999/HandBrake-WinUI/tree/467c0754ffc00a591fccefb3736b808a798b4534). Audit date: 2026-10-30.

This is a static comparison of the repository's WPF reference and WinUI implementation, not a claim of runtime parity or a comparison against every released HandBrake version. The accompanying [matrix](winui-wpf-parity-matrix.json) records 28 findings, checked source anchors, priorities and the reviewed file scope. Preferences is outside this audit. No build, Windows UI test or native encode was run.

## Main conclusion

Use WPF as the behavioral reference, then extract portable task and validation logic. Rewriting its XAML alone will leave the present functional gaps. Screenshots remain useful for spacing, responsiveness and interaction review; they are not required to discover most missing settings or engine mapping.

The WinUI project references App.Core and Interop, but the complete WPF EncodeTask, factory and queue service still live in the WPF project. App.Core currently supplies utilities, not that complete application domain. WPF enables WPF/Windows Forms; referencing that executable or copying its ViewModels wholesale is not the migration boundary.

Current WinUI already uses real native preset/job paths and has meaningful queue state handling. Native preset inheritance can preserve settings that its manual editors cannot expose. Thus “not editable” and “not passed to the engine” must be tracked separately. Conversely, creating a libhb job does not prove identical WPF defaults, overrides or successful encoding.

## Reuse boundary

| Component | Treatment | Dependency work |
| --- | --- | --- |
| libhb and Interop | Keep the same engine; reuse its public models/capability and picture helpers. | Do not change the engine to compensate for UI omissions. Preserve native ownership and lifecycle rules. |
| EncodeTask and ordered audio/subtitle outputs | Extract a neutral, versioned task snapshot with deep-copy semantics. | Trace model dependencies, enums, filter objects and serialization. One source track may have multiple output tracks. |
| PropertyChangedBase | Portable notification implementation is a reuse candidate. | It is a custom implementation; do not assume a UI framework dependency from its namespace. Move with namespace/dependency updates. |
| EncodeTaskFactory / preset mapping | Reuse behavior after extracting settings-policy dependencies. | Factory is internal and coupled to WPF task/settings types. Inject narrow policies; compare semantic jobs rather than JSON byte equality. |
| Geometry, audio/subtitle rules and validation | Extract pure calculations and rules before adding controls. | Retain native capabilities and compatibility constraints. WPF callsite wiring matters as much as method existence. |
| QueueTask, statistics and scheduling | Extract state and policy incrementally. | Replace UI dispatch, clocks, settings, worker lifecycle and platform hooks with explicit adapters. |
| ViewModelBase and WPF views | Reimplement presentation in WinUI. | Replace dialogs, window management, commands, dispatcher, clipboard/player integration and binding-specific behavior. |

This is an extraction plan, not a claim that these components have already been moved. Avoid a broad copy of WPF namespaces into WinUI or a second independent implementation of every rule.

## Ordered implementation

1. **Canonical task and encode preflight (P0).** Capture the complete resolved job and editable task state, preserve unknown native preset values, validate destination/source/compatibility once, and make Start current task work with an empty queue. Investigate the reported native error 3 from the failed attempt log and exact generated job; this audit does not establish its root cause or resolve it.
2. **Lossless Queue Edit (P0).** Save a versioned immutable snapshot with each entry. Rescan source, restore title/range/preset/custom changes, edit one setting, then replace that entry without silently discarding unrelated settings. Keep “Open source” distinct until this works.
3. **Geometry and ordered track rules (P0).** Keep rotation/padding independent of width/crop overrides. Support multiple audio outputs per source and complete subtitle compatibility/default rules before building their full editors.
4. **Complete controls and parity policies (P1).** Finish native filter/custom settings, codec quality direction, tune combinations, chapter import/export, MOV support and accurate preset modified comparisons. Then add stop-after-current, bulk queue tools and completion actions.
5. **Worker/hardware and scheduling (later).** Verify CPU correctness first. Make hardware availability explicit and test it separately; add isolation/concurrency only with resource ownership and cancellation tests.

Keep Windows 11 Fluent presentation, the independent settings/preview cards and the preview command inside its card. Keep the large drop target and text Close button. Functional parity does not require reproducing WPF spacing or its history-deletion policy.

## Acceptance evidence before claiming parity

- Compare normalized WPF/native and WinUI jobs for the same scanned fixture and preset. Account for default values, symbolic/numeric encoders and ordered tracks; raw JSON byte equality is insufficient.
- Round-trip a complex queue entry through Edit, changing exactly one setting; assert unrelated geometry, tracks, subtitles, chapter names, metadata, range and output path remain intact.
- Exercise manual crop with rotation/padding and two outputs from one audio source; inspect both generated jobs and produced media.
- Run a short CPU encode on Windows 11, retain full native logs/job JSON and verify output readability, duration, dimensions and tracks. Error 3 remains unconfirmed until this succeeds or its specific cause is diagnosed.
- Exercise pause/resume, stop-now/after-current, retry, completed-item skipping and interrupted restore with real callbacks. Check elapsed time excluding pauses.
- Verify quality slider endpoints per encoder and preset load → edit → modified → reload/save behavior.
- Use screenshots to verify compact density, clipping, tooltip scope and preview aspect ratio at narrow and maximized sizes. Do not infer functionality from a visible control.

Batch one Windows build after a coherent implementation milestone. Documentation validation in this audit only checks source references, IDs and JSON structure.
